# Бриф для UI/UX-дизайнера — плагин aa-market-monitoring

Плагин Alliance Auth 5.x для мониторинга собираемости EVE Online фитов и закупки дефицита. Интерфейс встраивается в стандартную тему Alliance Auth (Bootstrap 5). Все требования функциональности зафиксированы в `docs/TZ.md` (§14 «Интерфейс»); дизайн должен их сохранить, но может свободно прорабатывать компоновку и визуальный язык.

## 1. Контекст и аудитория

- Пользователи — корпоративные закупщики/координаторы EVE Online. Открывают дашборд регулярно, чтобы понять: «что можно собрать и что докупить».
- Ключевой сценарий: за 10–15 секунд оценить состояние по всем фитам и скопировать список закупки.
- Масштаб данных: 5–10 локаций, 20–100 фитов, таблица компонентов фита — 20–60 строк.

## 2. Роли и права (что видно каждой роли)

- `view` (только просмотр): дашборд, карточка фита, компоненты, цены, экспорт/копирование закупки.
- `edit`: дополнительно создание/правка/удаление фитов и компонентов, управление локациями, настройки, ручной запуск обновлений.
- Элементы управления `_edit` скрывать (не дизейблить) для `view`. SyncRun-лог виден только в `/admin/` — в UI не проектировать.

## 3. Страницы (маршруты фиксированы, компоновка — на усмотрение дизайнера)

| Страница | Содержимое |
|---|---|
| **Dashboard** (`index`) | Таблица фитов: имя, «K из N», статус, сумма докупки, счётчик оверпрайс-позиций, узкое место, время последней проверки. Фильтры: статус, область, узкое место. Сортировки. Сводная панель «итого докупить». Кнопка «Обновить сейчас» (edit). |
| **Карточка фита** (`fit_detail`) | Шапка: K/N, статус, сумма. Таблица компонентов (см. §4). Бейджи `OVERPRICE` / `NOT_COVERED`. Кнопки экспорта: буфер / `.txt` / `.csv`. |
| **Создание/правка фита** | Мастер: вставка EFT-текста → кнопка «Разобрать» → предпросмотр разбора → поля: имя, целевое количество N, область, overrides компонентов. Правка состава после разбора: добавить/удалить/изменить количество/сменить область. |
| **Удаление фита** | Экран подтверждения. |
| **Компоненты** (`components`) | Самостоятельный раздел меню рядом с Dashboard: тип, целевое количество, область, дефицит, стоимость. Компоновку (вкладка/секция) дизайнер может уточнить. |
| **Создание/правка компонента** | SDE-селектор типа (поиск по имени), количество, область, заметка. |
| **Локации** | Список локаций из SDE: статус синка, последняя синхронизация, вкл/выкл, добавление (регион → система → станция/структура). |
| **Настройки** | Наценка %, порог оверпрайса %, ставка доставки, интервалы синков, Jita, глубина стакана, webhook URL, язык, список провайдеров структур (приоритет, вкл/выкл, статус). |

## 4. Таблица компонентов (ядро карточки фита)

Колонки: компонент (имя + количество на фит) · область компонента · требуется (N·qᵢ) · доступно (A) · дефицит (Dᵢ) · `unit` · `ref` · стоимость · бейдж. Строка корпуса — визуально выделена (например, тонкая акцентная полоса или вес шрифта), но не ломает зебру/выравнивание чисел.

## 5. Визуальная система статусов (обязательная семантика цветов)

| Статус | Цвет | Смысл |
|---|---|---|
| `OK` | зелёный | K ≥ N |
| `DEFICIT` | оранжевый | 0 ≤ K < N |
| `HULL_MISSING` | красный | корпуса нет в области |
| `NO_DATA` | серый | только пустая область `L(S)=∅`; дефицит/стоимость **не показываются**, вместо них — баннер с причиной. Отдельная локация без данных — жёлтое предупреждение с id и нулевым вкладом, статус фита не меняется (решение №45) |

Представление собираемости: число «K из N» + прогресс-бар + цвет статуса. Узкие места — до 5 позиций, при большем — «и ещё N».

## 6. Обязательные UX-детали

- **Экспорт multibuy:** копирование в буфер через Clipboard API с подтверждением «Скопировано» (toast/инлайн). Экспорт всегда на английском, независимо от языка интерфейса.
- **Поллинг обновления:** кнопка «Обновить сейчас» запускает Celery-задачу; страница `refresh_status` отдаёт JSON для поллинга — спроектировать индикатор (spinner/прогресс), состояние «данные обновляются», ошибку и успех.
- **NO_DATA-баннер:** только при пустой области `L(S)=∅`; заметный, объясняющий («область не содержит локаций»), не пугающий красным. Отдельная локация без данных — жёлтое предупреждение с id и нулевым вкладом, статус фита не меняется (решение №45).
- **Oверпрайс:** бейдж `OVERPRICE` на строке компонента + счётчик оверпрайс-позиций в шапке/на дашборде.
- **Числовая типографика:** целые ISK с разделителями тысяч; количества целые; правое выравнивание чисел, monospace/tabular-nums; суммы — итоговой строкой.
- **Пустые состояния:** нет фитов / нет компонентов / нет локаций — дружелюбные подсказки с CTA (для edit-ролей).
- **Подтверждения:** удаление фита/компонента — явный confirm; destructive-действия визуально отличимы.

## 7. Современные тренды, уместные здесь

- Data-dense dashboard в стиле «control room»: чистые таблицы, sticky header, компактные строки, hover-подсветка.
- Status chips/бейджи вместо текстовых колонок; минимализм, отсутствие декоративного шума.
- Тёмная и светлая темы в рамках стандартной темы AA (Bootstrap 5 variables/tokens, не кастомный framework).
- Микроанимации только функциональные: обновление статуса, появление toast, прогресс поллинга.
- Responsive: дашборд на мобильном — приоритет 2, но таблицы должны деградировать прилично (горизонтальный скролл или карточная трансформация).

## 8. Ограничения (нельзя нарушать)

1. UI **никогда** не обращается к ESI — только чтение БД плагина; все «обновить» — через Celery-задачи.
2. i18n: все строки через gettext; язык интерфейса — en на этапе 1, но макеты должны оставлять запас для более длинных русских строк (~+30% ширины).
3. Webhook URL не показывается пользователям без `_edit`.
4. CSRF на всех формах; все view за login_required.
5. Производительность: дашборд ≤ 1 с при 100 фитах, карточка ≤ 500 мс — дизайн не должен предполагать тяжёлых клиентских фреймворков; серверный рендеринг Django-шаблонов + минимум JS.

## 9. Что сдать

1. Вайрфреймы/макеты: Dashboard, карточка фита, мастер создания фита (включая предпросмотр разбора EFT), Компоненты, Локации, Настройки.
2. Состояния: OK / DEFICIT / HULL_MISSING / NO_DATA, пустые состояния, состояние поллинга обновления, мобильная деградация таблиц.
3. Спецификация визуального языка: статусы, бейджи, числовая типографика, toast, баннеры — в терминах Bootstrap 5 / темы AA.
