# Настройка aa-market-monitoring

Все настройки редактируются на странице **Settings** (`market/`, URL name `settings`, доступ — роль `market_monitoring_edit`) и хранятся в singleton-модели `PluginSetting` (строка с `pk=1`). Права `_view` не видят форму настроек; webhook URL показывается только пользователям с `_edit`.

## Настройки PluginSetting

| Ключ | Тип | Default | Ограничения | Что влияет |
|---|---|---|---|---|
| `jita_markup_pct` | Decimal | 5 | 0…500 | Наценка m (процент), применяется к цене покрытия `unit` (не к доставке) |
| `overprice_threshold_pct` | Decimal | 25 | 0…1000 | Порог τ: бейдж `OVERPRICE`, если `unit` > `ref`·(1+τ/100), где `ref` — минимальная sell-цена Jita |
| `delivery_rate_isk_per_m3` | Decimal | 1250 | ≥ 0 | Ставка доставки ISK/м³; объём — `packaged_volume` типа; доставка без наценки |
| `jita_region_id` | Integer | 10000002 | — | Регион The Forge для стакана и цен Jita; входит в регионы синка только при включённой локации Jita IV-4 (см. эррату ниже) |
| `jita_station_id` | Integer | 60003760 | — | Станция Jita IV-4; синк стакана выполняется, только если эта станция добавлена и включена как локация в Locations UI |

| `provider_acl_cooldown_min` | Integer | 60 | 1…1440 | Cooldown провайдера при ACL-сбое (403/401) |

| `notification_deficit_cooldown_min` | Integer | 120 | 1…1440 | Общий cooldown повторной отправки неизменного `deficit`, `contracts_deficit` и `ships_deficit` |
| `webhook_url` | URL | — (пусто) | один канал | Discord webhook для уведомлений |
| `display_language_mode` | Enum | `client_default` | `client_default` \| `fixed_en` | Язык имён типов: `client_default` — `LANGUAGE_CODE` пользователя (fallback `en`); `fixed_en` — всегда английский |
| `contracts_sync_interval_min` | Integer | 30 | 5…1440 | Guard-интервал задачи `sync_contracts` (контракты — источник C) |
| `notification_contracts_deficit_enabled` | Boolean | True | — | Отправка уведомлений `contracts_deficit` (только при trigger=beat) |

Отдельной настройки включения или кулдауна для `ships_deficit` **нет**: новое событие делит `notification_deficit_enabled` и `notification_deficit_cooldown_min` с `deficit` (и тот же cooldown с `contracts_deficit`).

### Изменение интервалов без перезапуска beat

Beat дёргает задачи синка каждые 5 минут; каждая задача сама проверяет по `SyncRun`, истёк ли её guard-интервал (`jita_sync_interval_min`, `stock_sync_interval_min`, `contracts_sync_interval_min`, 60 мин для `verify_providers`, 24 ч для `cleanup_orphan_cache` и `sync_corp_structures`). Поэтому изменение интервалов в настройках применяется к следующему прогону **без перезапуска Celery beat**. То же верно для остальных настроек (наценка, пороги, глубина стакана, webhook). Рыночные синки и `sync_contracts` включены в beat; `sync_jita_book` — условный (см. ниже).

### Синк Jita зависит от локации

Beat по-прежнему дёргает `sync_jita_book` каждые 5 минут, но задача не делает ни одного ESI-запроса, если локация Jita IV-4 (`station_id = jita_station_id`) не добавлена или отключена в Locations UI. При выключенной Jita регион The Forge (`jita_region_id`) **жёстко исключается** из набора регионов §9.4 — в том числе если он пришёл из явного `scope_kind='region'/'system'` у фита/компонента или из SDE, — поэтому `sync_region_orders` тоже не обращается к рынку Jita. `JitaOrderLevel` и `MarketOrderCache(region, jita_region_id)` удаляются; недоступна **цена докупки**: `unit`, `ref`, `cost`, `shortfall`, `overprice_pct` не показываются (`&mdash;` / `None`), `Fit.total_cost=None`, бейджи `OVERPRICE` не показываются. Экспорт закупки (multibuy, `.txt`, `.csv`) остаётся доступным: он содержит все позиции с $D_i>0$, но без цен (`unit_price`/`cost` пустые). Статус фита, `K`, `D_i` и контракты продолжают считаться по добавленным/включённым локальным рынкам; это **не** `NO_DATA` по §6.7.

Проявление в UI: карточка фита и Dashboard показывают `&mdash;` вместо `0 ISK`, экспорт списка закупки содержит дефицитные позиции, но без цены, уведомления о дефиците (`deficit`, `contracts_deficit`, `ships_deficit`) не содержат стоимость. Полный `NO_DATA` с баннером и без расчёта дефицита/стоимости остаётся только при пустой области `L(S)` (§6.7, решение №45); отдельная локация без данных даёт нулевой вклад и предупреждение, но не меняет статус фита.

Кнопка «Обновить сейчас» ставит `sync_region_orders`, `sync_structure_orders`, `sync_contracts` и затем `recalc_stock_levels`. `sync_jita_book` добавляется только при включённой Jita: при выключенной/удалённой локации ручная цепочка состоит из **3 задач вместо 4** (без `sync_jita_book`); при включённой — из 4. Уведомления о дефиците при ручном запуске не отправляются. При выключенной Jita задача `sync_jita_book` (если дёрнута beat) и ежедневная очистка удаляют стакан и кэш региона без ESI-запроса и без ожидания интервала.

**Примечание (эррата к §9.4 и решениям №3/8/25/39 §20 ТЗ).** Решения №1–44 остаются в силе: Jita — The Forge, станция 60003760 (`jita_station_id`, настраивается, №3); обновление Jita и доступности — Celery с настраиваемыми интервалами (№8); оверпрайс — по минимальной sell-цене Jita и порогу-проценту (№25); Jita — только источник цен для докупки, `K` считается по `L(S)` (№39). Буква §9.4 предписывает безусловно добавлять регион Jita в объединение регионов синка; по явному указанию заказчика The Forge входит в регионы синка и `sync_jita_book` запускается только при добавленной и включённой локации `MarketLocation(kind=station, station_id=jita_station_id)` (Jita IV-4) в Locations UI. При удалённой/отключённой Jita ESI-запросов к рынку Jita нет ни в beat, ни в «Обновить сейчас»: The Forge жёстко исключается из регионов синка даже при явном `scope_kind='region'/'system'`, `JitaOrderLevel` и `MarketOrderCache(region, jita_region_id)` удаляются; цена докупки недоступна (`unit/ref/cost/shortfall/overprice_pct` — `None`/`&mdash;`, `Fit.total_cost=None`, OVERPRICE не показывается, экспорт закупки содержит дефицитные позиции без цен), а статус фита, `K`, `D_i` и контракты считаются по локальным рынкам; полный `NO_DATA` — только при пустой области `L(S)` (§6.7, решение №45), а локация без данных даёт нулевой вклад и предупреждение с id. При выключенной Jita ручная цепочка состоит из 3 задач вместо 4 (без `sync_jita_book`; при включённой — 4). Решения №1–44 не пересматриваются; по явному указанию заказчика в §20 добавлены только решения №45/№46, меняющие обработку отсутствия данных.

## Провайдеры структур

Структуры синкаются через персонажей AA с ACL на структуру. Токены плагин **не хранит** — используются токены AA (`esi.models.Token`) по `character_id` модели `eveonline.EveCharacter`.

### Привязка персонажа

1. CharLink запрашивает для `StructureProvider` скоупы `esi-markets.structure_markets.v1`, `esi-universe.read_structures.v1` и `esi-search.search_structures.v1` (последний — для поиска структур с правами дока). Если у персонажа скоупов нет — привязка отклоняется с текстом «добавьте персонажа с нужными скоупами».
2. Провайдер привязывается на странице Settings: приоритет (меньше = выше), включение/выключение.
3. Рекомендуется 2–4 провайдера.

**Примечание (эррата к решению №37 §20 ТЗ).** Решение №37 сохраняется полностью: тот же эндпоинт `GET /corporations/{corporation_id}/structures/`, beat раз в сутки, новые `MarketLocation(kind=structure)` с `enabled=false` и ручное включение в Locations UI, ACL-сбои — по §11. В тексте ТЗ идентификатор скоупа опечатан: `esi-corporations.read_corporation_structures.v1` — несуществующий scope, SSO/CharLink отклоняет его как `invalid_scope`. Фактически для синка структур корпораций запрашивается `esi-corporations.read_structures.v1` (корректный scope из официальной OpenAPI-спеки ESI). Решения №1–44 не пересматриваются; по явному указанию заказчика в §20 добавлены только решения №45/№46, меняющие обработку отсутствия данных.

### Поведение при сбоях

| Ситуация | Реакция |
|---|---|
| Успешный запрос (200) | `acl_fail_count = 0`, `status = ok` |
| 403/401 | `acl_fail_count += 1`, `status = cooling_down`, `cooldown_until = now + provider_acl_cooldown_min` (default 60 мин); структура в том же прогоне переобрабатывается **следующим** провайдером |
| `acl_fail_count >= provider_acl_max_failures` (default 3) | `status = disabled` + алерт `provider_acl_lost` («отключён») |
| Провайдеров с доступом нет | локация получает `sync_status = no_provider` и даёт вклад 0 в доступность; фиты считаются по оставшимся локациям, в причинах пересчёта и UI — предупреждение с id локации (решение №45); `NO_DATA` — только если область пуста |

Провайдер в статусе `disabled` включается **только вручную** через форму провайдеров; при включении счётчик сбоев сбрасывается. Задача `verify_providers` (раз в час) проверяет доступ провайдера к структурам через ESI и обновляет `last_verified_at`; счётчик сбоев меняется только при фактическом 403/401.

### Провайдеры контрактов

`ContractProvider` — персонаж AA с источником `corporation` (корпоративные и альянсовые контракты) или `character` (персональные); токены плагин не хранит, используются токены AA. CharLink запрашивает для него скоупы `esi-contracts.read_corporation_contracts.v1`, `esi-contracts.read_character_contracts.v1` и `esi-corporations.read_structures.v1` (последний — для `sync_corp_structures`, см. эррату выше). Список персонажей в форме Settings ограничен владельцами текущего пользователя AA (`character_ownership`): чужие персонажи не показываются и не принимаются POST. Задача `sync_contracts` (guard — `contracts_sync_interval_min`) кэширует открытые `item_exchange` контракты и их позиции, дедуплицируя по `contract_id`. Нет включённого провайдера с свежим успешным синком (`sync_status = ok`, `last_synced_at >= now - data_stale_after_min`) → `contracts_status_cache = no_data` → общий `ships_status_cache = no_data`: фит исключается из сводных сумм C+K.

## Discord webhook

Настраивается один webhook (`webhook_url`) — один канал. HTTP POST JSON (`requests`), таймаут 10 с, 3 ретрая с backoff 2/4/8 с; результат пишется в `NotificationLog` (`ok`, `error`). Пример значения (маскировано):

```
https://discord.com/api/webhooks/1234567890/XXXXXXXXXXXXXXXXXXXXXXXX
```

События:

| Событие | Когда | Цвет embed |
|---|---|---|
| `deficit` | beat-проверка, K < N: фит, K/N, узкие места (до 5), сумма докупки, число оверпрайс-позиций, ссылка | оранжевый |
| `contracts_deficit` | beat-проверка, C < N: фит, C/N кораблей в контрактах, нехватка N−C, область, ссылка | оранжевый |
| `ships_deficit` | beat-проверка, `ships_status_cache='deficit'` (C+K < N): фит, C+K и N, нехватка N−(C+K), раздельно C и K, область, ссылка | оранжевый |
| `hull_missing` | корпус отсутствует в области | красный |
| `provider_acl_lost` | ACL-сбой / отключение провайдера | красный |
| `sync_failed` | задача упала / превышен порог ошибок (только при переходе состояния) | красный |
| `sync_recovered` | успешный прогон после серии failed (с длительностью простоя) | зелёный |

Дедупликация `deficit`: уведомление отправляется, если изменился хэш состояния (fit_id ‖ K ‖ набор дефицитных типов ‖ округлённый Total) **или** прошло ≥ `notification_deficit_cooldown_min` с последней ok-отправки при сохраняющемся дефиците. У `contracts_deficit` свой хэш (fit_id ‖ C ‖ N) и свой флаг включения `notification_contracts_deficit_enabled`, но тот же cooldown. У `ships_deficit` свой хэш (fit_id ‖ `ships_status` ‖ `ships_deficit`); отправка при изменении хэша либо по `notification_deficit_cooldown_min`, управление — через `notification_deficit_enabled`. Хэши и записи `NotificationLog` у трёх событий независимы: изменение одного не перезаписывает состояние другого. Системные события (`provider_acl_lost`, `sync_failed`, `sync_recovered`) отправляются только при переходе состояния. Уведомления о дефиците — **только при автоматическом (beat) запуске**; ручной запуск их не порождает, включая `ships_deficit`.

## Диагностика NO_DATA

Различаются три случая.

1. **Пустая область (§6.7, решение №45) → `NO_DATA`.** Область `L(S)` не резолвится ни в одну локацию: система/регион без NPC-станций и включённых структур либо неизвестный `scope_ref`. Дефицит, стоимость и `C+K` **не рассчитываются**, уведомление о дефиците не отправляется, в UI показывается причина и баннер. Для компонента вне фитов проверяется его собственная область.
2. **Локация области без свежих данных (§6.7, решение №45) → вклад 0, но не `NO_DATA`.** Причины: структура с `sync_status != ok` (`failed`/`partial`/`no_acl`/`stale`), `no_provider`, пустой или протухший `last_synced_at`, отсутствие строки `StockLevel`, региональный синк, не завершавшийся успешно за `data_stale_after_min`. Такая локация даёт вклад $A_t^{l}=0$; суммирование по локациям области выполняется **до** деления на $q_i$. Статус фита, `K`, $D_i$, цена покрытия, стоимость, `C+K` и уведомления считаются по общему правилу по всем локациям области с нулевым вкладом проблемных. В причинах пересчёта и в UI карточки фита/дашборда показывается предупреждение с **id локации** и причиной; из-за одной такой локации фит не переводится в `NO_DATA`.
3. **Нет Jita → цена докупки недоступна, но не `NO_DATA`.** При удалённой/отключённой локации Jita IV-4 стакан и кэш чистятся; `unit`, `ref`, `cost`, `shortfall`, `overprice_pct` не показываются (`&mdash;` / `None`), `Fit.total_cost=None`, OVERPRICE не показывается. Экспорт закупки содержит дефицитные позиции без цены (`unit_price`/`cost` пустые). Статус фита, `K`, `D_i` и контракты продолжают считаться по добавленным/включённым локальным рынкам; уведомления о дефиците не содержат стоимость (см. эррату выше).

Для сводки `C+K` действует то же правило на уровне источников: `no_data` у `C` (нет включённого `ContractProvider` либо нет свежей успешной синхронизации) или у `K` (пустая область рыночного скоупа) даёт `ships_status_cache='no_data'`. Агрегатный дефицит в этом случае не считается, `ships_deficit` не отправляется, фит исключается из `∑C`, `∑K` и `∑(C+K)`. Локация рынка без данных сама по себе `no_data` у `K` не даёт: её вклад в доступность 0, и фит **остаётся** в сводке (решения №43, №45; §18.9, §19.18).

### Причины: пустая область и предупреждение по локации (§6.7 ТЗ)

**Пустая область → `NO_DATA`:** система/регион без NPC-станций и включённых структур либо неизвестный `scope_ref`. Для `station` в `L(S)` всегда одна локация; проверьте, что `scope_ref` указывает на существующую запись SDE.

**Локация без данных → вклад 0 + предупреждение (без `NO_DATA`):**

1. **Структура без свежего синка:** `sync_status != ok`, нет доступного провайдера (`no_provider`), пустой или протухший `last_synced_at`.
2. **Отсутствие агрегата:** по локации нет строки `StockLevel` (данные ещё не синкались/не агрегировались).
3. **Протухшие данные:** `last_synced_at` локации старше `data_stale_after_min` (default 180 мин), по нужной NPC-станции нет свежей строки `StockLevel` (`updated_at` не старше порога) либо региональный синк не завершался успешно за тот же период. Для NPC-станции пустой `last_synced_at` не считается протухшим, если свеж региональный `StockLevel`; `sync_status=stale` сам по себе статус фита не меняет.

**Важно (решение №46).** При успешном **полном** синке локации, по которой заказов нет, в `StockLevel` пишется нулевой агрегат для каждого нужного типа; при исчезновении заказов старые строки удаляются полной заменой. `partial`-синк нулевые агрегаты **не** пишет — по такой локации остаётся нулевой вклад и предупреждение до успешного полного синка.

Выключенная Jita **не** входит в причины `NO_DATA` по §6.7: это потеря только цены докупки, описанная выше.

**Строгий scope (§5.1).** Добавление ещё одной NPC-станции в Locations не расширяет область фита со `scope_kind='station'`: `L(S)` остаётся `{station_id}`, и доступность берётся только из `StockLevel` этой станции. Другие станции, системы и структуры учитываются только в областях `system`/`region` (в том числе через `scope_override` компонента). Новая запись в Locations поэтому не подменяет отсутствующие данные по станции, на которую скоупится фит: пока по ней нет данных, её вклад в `A` равен 0 и показывается предупреждение с id.

### Как смотреть статус локаций

- Страница **Locations** (`_edit`): для каждой локации — статус синка (`ok` / `no_acl` / `error` / `no_provider` / `stale` / `partial`) и время последней синхронизации.
- Для NPC-станции чип `stale` и пустой `last_synced_at` — ожидаемое состояние сразу после добавления: данные приходят региональным синком, а не структурным. Пока по станции есть свежая строка `StockLevel`, предупреждения по ней нет; чип сменится на `ok` после очередного успешного `sync_region_orders`. Если свежей строки нет — вклад станции 0 и предупреждение с её id. Для структуры `stale`, `failed` и пустой `last_synced_at` означают, что структурный синк ещё не прошёл: вклад структуры 0 и предупреждение с id, но фит не становится `NO_DATA`, пока область не пуста.
- Django-admin (`/admin/`, суперпользователь): модели `MarketLocation`, `StructureProvider`, `SyncRun` — история прогонов задач с триггером (`beat`/`manual`), статусом (`ok`/`partial`/`failed`) и текстом ошибок.

### Что делать

| Симптом | Действие |
|---|---|
| `no_provider` | Привязать/включить провайдера с нужными скоупами (см. выше). Пока провайдера нет, вклад локации в доступность 0 и в UI — предупреждение с id локации; это не `NO_DATA`, если область не пуста |
| `no_acl` | У провайдера нет ACL на структуру — выдать доступ персонажу-провайдеру в игре; до успешного синка вклад локации 0 и предупреждение с id |
| `stale` / пустой `last_synced_at` у **структуры** | Проверить, что Celery worker и beat работают; привязать/включить провайдера, нажать «Обновить сейчас», проверить `SyncRun` в admin. Пока данных нет — вклад 0 и предупреждение, дефицит/стоимость считаются по остальным локациям |
| `stale` / пустой `last_synced_at` у **NPC-станции** | Чип `stale` и пустой `last_synced_at` сами по себе не требуют действий, если есть свежая строка `StockLevel`: предупреждения по этому признаку нет. Протухший `last_synced_at` даёт вклад 0 и предупреждение даже при свежей строке; если строки нет — тоже вклад 0 и предупреждение с id. Нажать «Обновить сейчас» и проверить `sync_region_orders` в `SyncRun` |
| Задачи `failed` | Текст ошибки в `SyncRun.errors`; часто — лимиты ESI (задача переносится на следующий прогон) или неверные токены AA. До успешного синка локация даёт 0 и предупреждение |
| Задачи `partial` | Проверить `SyncRun.errors` и лимиты ESI; `partial`-синк не пишет нулевые агрегаты (решение №46), поэтому локация продолжает давать 0 и предупреждение до полного успешного синка |
| Регион синк OK, но локация даёт 0 | Проверить, что `data_stale_after_min` больше интервала синка, что регион локации входит в синк (объединение регионов включённых локаций и областей расчёта) и что свежая строка `StockLevel` есть по каждой нужной NPC-станции; для структуры — `sync_status=ok` и свежий `last_synced_at` |
| `NO_DATA` с баннером, дефицит/стоимость не считаются | Искать причину в пустой области: `L(S)=∅` (система/регион без NPC-станций и включённых структур, неизвестный `scope_ref`). Свежесть локальных локаций, `StockLevel` и `no_provider` причинами `NO_DATA` не являются — они дают 0 и предупреждение |
| `ships_status_cache='no_data'` при исправном рынке | Проверить `contracts_status_cache`: включить `ContractProvider` с нужными скоупами и дождаться успешного `sync_contracts` в интервале `data_stale_after_min`. Пустая область рыночного скоупа — вторая причина `no_data` у `K` |
| Предупреждение с id локации и нулевым вкладом в `K` | Сверить причину с таблицей выше; это ожидаемое поведение при `failed`/`partial`/`no_provider`/`stale`/отсутствии `StockLevel`. Фит остаётся в `∑C`, `∑K`, `∑(C+K)`, если обе величины известны |
| Цена докупки показывает `&mdash;` (`unit`/`ref`/`cost`/`shortfall`/`overprice_pct`), `Fit.total_cost=None`, в экспорте нет цен, но статус/`K`/`D_i` посчитаны | Добавить и включить локацию Jita IV-4 (`jita_station_id`) на странице Locations; дождаться успешного `sync_jita_book` (при выключенной Jita эту задачу ручной запуск не ставит) |

Примечание: ESI кэширует ответы (регион ≈ 5 мин, структуры ≈ 30 мин) — это ожидаемое поведение.
